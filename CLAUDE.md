# Yellow Club Agent

## 1. Краткое описание проекта

Yellow Club Agent — это Telegram-бот и Telegram Mini App для автоматизации операционных процессов детского образовательного клуба Yellow Club: клиентский кабинет, оплаты и их автоматизация, уведомления и рассылки, onboarding клиентов, сбор доступности (Availability) для расписания и workspace формирования расписания на новый учебный год. Проект интегрирован с CRM МойКласс (МК) как источником данных об учениках, группах и занятиях.

## 2. Текущие рабочие возможности

Ниже — только реально существующие в коде функции. Там, где функция доступна не всем, а только через pilot-флаг/allowlist, это указано явно.

- Telegram-бот (`bot.py`, `handlers.py`) — работа в личке и группах, smart-режим ответов, заявки на пробное занятие.
- Telegram Mini App (`miniapp/`, `web_app_server.py`) — единая точка входа для сотрудников и клиентов, роль определяется сервером.
- Кабинеты сотрудников (owner/admin/operations/client_manager/teacher/senior_teacher/methodist/intern/director/kitchen) — раздельная навигация и права по ролям.
- Клиентский кабинет: regular/combined-клиенты используют новый unified cabinet (`client_cabinet_v7113_*`, включён pilot-флагом/allowlist, по умолчанию выключен глобально).
- Отдельный food-only flow — не использует новый client cabinet, отдельная логика.
- Автоматизация счетов и оплат (invoice automation, ERIP/bePaid эквайринг) — управляется отдельными env-флагами (`PAYMENT_INVOICE_AUTOMATION_ENABLED` и др.), safe-by-default (discovery on, create/publish off, пока явно не включено).
- Клиентские уведомления (`client_notifications_*`) и рассылки/«Коммуникации» (`client_communications_*`) — оба блока включаются отдельными pilot-флагами, отправка и планировщик — отдельными kill-switch'ами.
- Onboarding по CL-кодам и mass-onboarding кампаниям с invite-ссылками.
- Availability — сбор доступности родителей для расписания (существующая, стабильная функция, не путать со schedule workspace).
- Schedule workspace («Расписание», v7.1.17+) — реконструкция групп прошлого учебного года из МойКласс, определение продолжающих учеников, сопоставление с Availability, локальные черновики расписания. Включается флагом `SCHEDULE_FOUNDATION_ENABLED` (по умолчанию выключен, первый деплой — только owner-pilot), синхронизация с МойКласс и мутации черновиков — отдельные флаги.
- Локальные schedule snapshots и drafts — версионированные локальные таблицы (`schedule_source_*`, `schedule_draft_*`), МойКласс используется только на чтение.
- Feature flags — все крупные блоки функциональности (client cabinet, коммуникации, schedule workspace, invoice automation и т.д.) управляются env-флагами, по умолчанию выключены или ограничены pilot-allowlist.

## 3. Архитектура

- **`bot.py`** — точка входа Telegram-бота: собирает `Storage`, `AgentCore`, `AdminPanel`, `BotHandlers` и запускает polling.
- **`handlers.py`** — обработка входящих сообщений и callback-запросов бота, команды, онбординг-кнопки.
- **`web_app_server.py`** — HTTP API сервер Mini App (`http.server`/`ThreadingHTTPServer`), все `/api/...` роуты и бизнес-методы `MiniAppContext`. Самый крупный файл проекта — организован по тематическим секциям с заголовками-баннерами (например, `# v7.1.17 — SCHEDULE MODULE`).
- **`storage.py`** — единственный слой доступа к SQLite. Инициализация схемы, миграции (`CREATE TABLE/INDEX IF NOT EXISTS`, аддитивные `ALTER TABLE`), CRUD и доменные запросы для всех модулей. Тоже организован по секциям.
- **`config.py`** — `Settings` (frozen dataclass) и `load_settings()`: чтение `.env`, все feature flags и pilot-allowlist'ы.
- **`schedule_domain.py`** — чистая логика schedule-модуля без I/O: определение доминантного слота занятий, resolve continuation-статуса, сопоставление с Availability. Аналог `payment_domain.py` для платежей.
- **`schedule_sync.py`** — оркестрация read-only синхронизации с МойКласс для schedule-модуля (retry/backoff, прогресс, resume).
- **`moyklass_client.py`** — клиент API МойКласс и разбор его ответов.
- **`payment_domain.py`** — чистая доменная логика платежей (статусы, каналы, дедупликация).
- **`miniapp/`** — фронтенд Mini App: `index.html`, `app.js` (весь UI на vanilla JS, без фреймворка и без сборки), `styles.css`.
- **`tests/`** — unittest-файлы, по одному-нескольким на фичу/релиз, с суффиксом версии в имени (`test_<feature>_v<version>.py`).
- **`storage/`** — рантайм-каталог для локальной SQLite БД (`messages.db`), не хранит код, в git не коммитится.
- **`data/`** — база знаний бота в markdown (используется `knowledge_base.py`).

## 4. Локальный запуск

```bash
# создание виртуального окружения
py -3.12 -m venv .venv
# или
python -m venv .venv

# активация (Windows PowerShell)
.venv\Scripts\Activate.ps1

# установка зависимостей
.venv\Scripts\python.exe -m pip install -r requirements.txt

# запуск бота
.venv\Scripts\python.exe bot.py

# запуск Mini App сервера
.venv\Scripts\python.exe web_app_server.py
```

На Windows есть готовые скрипты: `start_windows.bat` (бот), `start_miniapp_windows.bat` (Mini App), `reset_venv_windows.bat` (пересоздать `.venv`).

Локальная разработка Mini App без Telegram: `WEB_APP_DEV_MODE=true` в `.env` включает вход через `?dev_user_id=<id>` вместо реального Telegram `initData`.

Статические проверки перед коммитом:

```bash
node --check miniapp/app.js
python -m py_compile <изменённые .py файлы>
git diff --check
```

Запуск отдельного теста:

```bash
python -m unittest tests.test_<имя_файла> -v
```

Важно:
- production systemd-сервисы использует только владелец проекта; разработчики не выполняют deploy самостоятельно.
- локальная среда должна использовать локальную SQLite БД (`storage/messages.db`), никогда не production-БД.

## 5. Тестирование

- Для конкретной задачи сначала пишутся/запускаются **targeted tests** — тесты именно этой фичи.
- Затем — **regression-группы** для функций, которые теоретически могло задеть изменение (не полный `full suite` — по времени это избыточно для рядовой задачи, но targeted и relevant regression tests обязательны).
- `node --check miniapp/app.js` — обязательно при любом изменении `app.js`.
- `python -m py_compile` — обязательно для каждого изменённого `.py`-файла.
- `git diff --check` — проверка на конфликтные маркеры/висящие пробелы перед коммитом.
- UI-задачи проверяются реальным рендером (Playwright или ручной браузер) на мобильных viewport'ах — недостаточно только строковых/CSS-проверок в unittest, чтобы считать UI-фичу исправленной.
- Полный full suite не запускают без необходимости — это долго; но targeted и relevant regression tests для затронутой области — обязательны перед commit.

## 6. Coding conventions

- Стек — Python (stdlib `http.server`, без веб-фреймворка) и vanilla JS на фронтенде. Не переписывать проект на новый framework.
- Type hints — там, где они уже используются в затронутом файле (`storage.py`, `schedule_domain.py` и т.д. используют аннотации, часть старого кода — нет; не выполнять глобальный рефакторинг типов ради задачи).
- Понятные, стабильные `reason_code` в JSON-ответах API (`"forbidden"`, `"feature_disabled"`, `"version_conflict"`, `"not_found"` и т.п.) — фронтенд и тесты полагаются на них, не переименовывать существующие без необходимости.
- Проверка ролей и feature flags — всегда на сервере (`_role_for_user`, `_require_*_access`), никогда не доверять роли/флагу из фронтенда.
- Идентификация клиентов и учеников — только по устойчивым ID (`mk_user_id`, telegram `user_id`, внутренние `id`); никогда не использовать имя как уникальный ключ.
- Длинные списки — только через server-side pagination (`limit`/`offset`, клампится на сервере), никогда не отдавать тысячи строк в DOM.
- Обращения к МойКласс — без неконтролируемого N+1 (на группу/ученика); при добавлении новой интеграции заранее считать ожидаемое количество запросов.
- Мутирующие операции — идемпотентны там, где возможен повтор (double-submit, retry, resume).
- Мутации, важные финансово или операционно, — с audit trail (кто/когда/что изменил).
- SQLite-миграции — только аддитивные и самоприменяющиеся (`CREATE TABLE/INDEX IF NOT EXISTS`, аддитивный `ALTER TABLE`), выполняются при инициализации `Storage`, не требуют отдельного migration-раннера.
- Никаких destructive migrations (`DROP`, разрушающий `ALTER`) без отдельного согласования с владельцем.

## 7. Работа с Git

- Прямой push в `main` запрещён.
- Одна задача — одна ветка (`feat/`, `fix/`, `chore/`, `test/`, `integration/` + короткое имя задачи).
- Одна задача — отдельный `git worktree`, чтобы параллельные Claude Code не задевали рабочие каталоги друг друга.
- Ветка создаётся от актуального `origin/main` (`git fetch origin` перед созданием).
- Не использовать `git add .` / `git add -A` — добавлять только конкретные файлы задачи.
- Не использовать `git reset --hard`, `git clean` без явного разрешения.
- Не переписывать чужие коммиты, не делать force-push без отдельного разрешения.
- Перед коммитом — просмотреть `git diff` построчно.
- После push — проверить `HEAD == origin/<branch>`.
- Merge в `main` — только после проверки отчёта и согласования (не выполняется автоматически исполнителем задачи).

## 8. Параллельная работа

- Два Claude Code могут работать одновременно, каждый в своём `git worktree` и своей ветке.
- Каждый промт задачи явно перечисляет разрешённые и запрещённые для изменения файлы/области.
- Нельзя менять файлы, принадлежащие активной задаче другого разработчика (см. `docs/ACTIVE_WORK.md`).
- «Горячие» файлы, где пересекаются почти все задачи (`storage.py`, `web_app_server.py`, `miniapp/app.js`, `miniapp/styles.css`), — при пересечении задачи не выполняются параллельно без integration-плана (см. `docs/WORKFLOW.md`).
- При необходимом пересечении — изменения делаются последовательно либо через отдельную integration-ветку.
- Планирование задач, границ и проверка отчётов — на стороне человека/GPT-координатора; Claude Code исполняет конкретную назначенную задачу и не расширяет scope самостоятельно.

## 9. Хрупкие места и неизменяемые правила

### Оплаты
- Не менять семантику Payment Automation без отдельной задачи.
- Не создавать повторные счета/публикации — дедупликация обязательна.
- Сохранять idempotency всех платёжных мутаций.
- Не менять withdrawal semantics.
- Не менять логику постинга оплат в МойКласс без отдельного разрешения.

### Клиентский кабинет
- Regular и combined клиенты используют новый (v7.1.13+) cabinet.
- Food-only остаётся на старом flow — не переводить автоматически на новый cabinet.
- CL-коды/invite не должны менять food-связи.
- Регистрация в food-модуле не должна автоматически создавать regular-связь клиента.

### Onboarding
- Доверенные связи parent ↔ child не дублируются.
- Повторный CL-код/invite должен быть безопасным (идемпотентным), не ломать существующую связь.
- Invite-токены никогда не выводятся в логи/UI за пределами предназначенного получателя.

### Роли
- Backend принимает решение по реальной роли пользователя (`_role_for_user`), никогда не по значению от фронтенда.
- Test role (переключатель тестовой роли в UI) используется только для визуальной проверки UI, никогда не заменяет реальную роль в backend-проверках прав.
- `client_manager` не получает доступ уровня owner/admin.

### МойКласс
- Read-only операции не превращать в write без отдельной, явно согласованной задачи.
- Schedule-модуль никогда не создаёт и не изменяет группы/занятия в МойКласс.
- Не создавать N+1 запросов по группам или ученикам — считать бюджет запросов заранее.
- Не хранить полные необработанные payload'ы МойКласс без необходимости (только нужные поля).

### Расписание (Schedule workspace)
- Snapshot неизменяем (immutable) после успешной активации.
- Незавершённый (неполный) snapshot никогда не активируется.
- Черновики (drafts) не меняют исходный source snapshot.
- Мутации черновиков управляются отдельным feature flag от самой видимости модуля и от синхронизации.
- Пробное/отработка/разовое занятие нельзя считать регулярным составом группы без явного доказательства (доминантный слот, несколько посещений).

### База данных
- Production DB никогда не копируется в git.
- Резервные копии БД не добавляются в git.
- Все изменения схемы должны безопасно применяться к уже существующей БД (аддитивно, без потери данных).

## 11. Текущая активная разработка

Полный текущий список активных задач и их владельцев — в [`docs/ACTIVE_WORK.md`](docs/ACTIVE_WORK.md). История релизов подробно не хранится в этом файле.

## 12. Формат финального отчёта Claude

Каждый финальный отчёт по задаче должен содержать:
- что реализовано;
- impact map (что и почему затронуто);
- изменённые файлы;
- migrations (если были);
- tests (какие запущены, результаты);
- реальные результаты проверок (не предположения);
- failure modes, которые были рассмотрены;
- commit hash;
- подтверждение push;
- git status после push;
- подтверждение отсутствия production deploy/production access;
- известные ограничения (known limitations).

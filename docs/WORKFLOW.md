# Workflow

Процесс выполнения одной задачи в репозитории Yellow Club Agent, от постановки до merge.

## Основной процесс

```
Задача
  → отдельная ветка (от актуального origin/main)
  → отдельный worktree
  → аудит (изучить фактический код перед изменениями)
  → реализация
  → targeted tests
  → regression tests (для затронутых областей)
  → commit
  → push
  → отчёт
  → review
  → integration
  → merge
```

- **Задача** — конкретный task prompt с явным списком разрешённых и запрещённых файлов/областей.
- **Отдельная ветка** — `feat/`, `fix/`, `chore/`, `test/` или `integration/` + короткое имя задачи, всегда от актуального `origin/main` (`git fetch origin` перед созданием ветки).
- **Отдельный worktree** — `git worktree add ../yellow_club_agent_<task> -b <branch> origin/main`, чтобы не пересекаться с рабочим каталогом другого разработчика.
- **Аудит** — перед написанием кода изучить реальную структуру и логику затронутых файлов; не придумывать архитектуру или команды, которых нет в репозитории.
- **Реализация** — только в пределах разрешённых задачей файлов.
- **Targeted tests** — тесты именно этой фичи/исправления.
- **Regression tests** — тематические группы тестов для функций, которые теоретически могло задеть изменение; полный full suite не запускается без необходимости.
- **Commit** — точечное добавление файлов (`git add <файл>`, никогда `git add .`/`git add -A`), просмотр `git diff` перед коммитом.
- **Push** — в свою ветку, не в `main`; после push — проверка `HEAD == origin/<branch>`.
- **Отчёт** — по формату из `CLAUDE.md`, раздел 12.
- **Review** — координатор (владелец/GPT-координатор) проверяет отчёт и diff.
- **Integration** — при пересечении с другой активной задачей изменения интегрируются последовательно или через отдельную integration-ветку (см. ниже).
- **Merge** — в `main` только после review и согласования; не выполняется исполнителем задачи автоматически.

## Предотвращение конфликтов

**Горячие файлы** — почти в каждой задаче есть шанс их задеть, поэтому они требуют особого внимания при планировании параллельных задач:

- `storage.py`
- `web_app_server.py`
- `miniapp/app.js`
- `miniapp/styles.css`
- `handlers.py`
- `config.py`

Правила:

- Не назначать одновременно две задачи, затрагивающие одинаковые горячие файлы, без явного integration-плана.
- Если пересечение необходимо — одна ветка становится базовой (мержится первой), вторая ветка интегрируется на неё уже после мержа первой.
- Конфликт при merge/rebase **не разрешается** автоматическим выбором «ours»/«theirs» — только построчный анализ обеих сторон изменения.
- После интеграции повторно запускаются targeted-тесты **обеих** задач, участвовавших в пересечении, чтобы подтвердить, что объединение не сломало ни одну из них.

## Шаблон handoff

При передаче задачи на review или интеграцию заполняется краткий handoff:

```
branch:              <имя ветки>
base commit:         <commit, от которого создана ветка>
task:                <краткое описание задачи>
allowed files:       <список файлов/областей, разрешённых task prompt>
forbidden files:     <список файлов/областей, запрещённых task prompt>
migrations:          <да/нет, какие>
tests:               <какие targeted/regression группы запущены, результат>
commit:              <commit hash после push>
known limitations:   <что сознательно не сделано или требует отдельной задачи>
```
